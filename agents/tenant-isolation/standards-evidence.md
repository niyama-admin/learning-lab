# Multi-tenant data isolation: what standards and vendor guidance actually say

## Bottom line

1. No standard I could read mandates a tenancy model (row-level, schema, database, or account per tenant). They require outcomes: separation, access control, logging, encryption "appropriate to risk", deletion. A pooled model with tenant_id plus row-level security (RLS) is not forbidden by any text I read.
2. Two texts push toward stronger, testable separation. PCI DSS v4.0 App. A1 (only if you are a multi-tenant service provider handling card data) requires logical separation, per-customer access limits, per-customer logs, and a 6-monthly pen test of the separation. FedRAMP guidance requires 3PAOs to test tenant-to-tenant. Both say "logical separation" is acceptable and need evidence it works.
3. NIST SP 800-144 states the real risk plainly. Public clouds rely on "logical separation at multiple layers of the application stack", and a configuration or software error can expose one tenant's data to another. That is the argument for defence in depth (RLS plus app checks plus tests), not for a specific model.
4. Vendor guidance (AWS, Azure) treats isolation as a spectrum and recommends a mix (AWS "bridge", Azure "vertically partitioned"). Azure states RLS is often skipped "because of those complexities". Qdrant (vendor) says per-tenant collections are "rarely the most efficient" and caps Qdrant Cloud at 1000 collections per cluster by default.
5. Agent-specific: shared caches are a documented cross-tenant leak surface. A peer-reviewed-style arXiv audit found global prompt-cache sharing across users in 7 API providers. Anthropic and OpenAI document cache isolation by organisation (Anthropic also by workspace on some platforms). OWASP lists multi-tenant vector DB context leakage. Tenant-scoped retrieval and cache keys are the minimum.
6. Gaps: ISO 27001/27017/27018, AICPA TSC text, CCM control text, and HIPAA HHS cloud guidance were not readable from primary sources (see end). Do not quote them as verified.

## Documented trade-offs per model (vendor/primary docs only)

Terms: AWS "pool" = shared resources (tenant_id style); "silo" = dedicated resources; "bridge" = mix per component.

**Pool / tenant_id column (+ RLS)**
- AWS: pooled data is "co-mingled and partitioned based on a tenant identifier"; partitioning does not ensure isolation, which "must still be applied separately". Source: https://docs.aws.amazon.com/whitepapers/latest/saas-architecture-fundamentals/data-partitioning.html (marked "historical reference only").
- AWS: authentication and authorization are not isolation: "a user could be authenticated and authorized, and still access the resources of another tenant." https://docs.aws.amazon.com/whitepapers/latest/saas-architecture-fundamentals/tenant-isolation.html
- PostgreSQL RLS: no policy means default-deny; superusers and BYPASSRLS roles always bypass; table owners bypass unless `FORCE ROW LEVEL SECURITY`; referential-integrity checks bypass RLS and can leak via "covert channel"; backups can silently omit rows unless `row_security` is off. https://www.postgresql.org/docs/current/ddl-rowsecurity.html (raw/pg_rls.txt)
- Azure: RLS needs user and tenant identity propagated into every query; "can be complex to design, implement, test, and maintain. Many multitenant solutions don't use row-level security because of those complexities." https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/storage-data
- Azure: single shared DB makes per-tenant restore hard ("restore the database to a separate resource and selectively recover that tenant's data"); sharded or dedicated DBs give more granular recovery. Same page.
- Azure SQL patterns page: single multitenant DB is simplest but "long before [scale limit] the database becomes unwieldy"; per-tenant point-in-time restore is the cited example of an operation that gets slow. https://learn.microsoft.com/en-us/azure/azure-sql/database/saas-tenancy-app-design-patterns?view=azuresql (last updated 2025-08-21)
- Noisy neighbour: one tenant's load degrades another's; a shared storage account throttle hits all tenants (Azure storage-data page above; https://learn.microsoft.com/en-us/azure/architecture/antipatterns/noisy-neighbor/noisy-neighbor).
- Cost: higher tenant density, lower cost (Azure storage-data page). Moving a tenant between tenants can be an identifier/key update, no data migration (Azure tenancy-models page).

**Table per tenant / schema per tenant**
- No primary source I read gives numbers or a dedicated trade-off discussion for schema-per-tenant or table-per-tenant in relational DBs. Azure mentions "separate tables in shared databases" as an option only. AWS gives DynamoDB table-per-tenant as the siloed example. Treat schema-per-tenant limits (catalog bloat, migration fan-out, connection limits) as NOT VERIFIED from primary docs.

**Database per tenant**
- Azure SQL patterns table (standalone app vs database-per-tenant vs sharded multitenant): scale "Medium (1-100s)" / "High (1-100,000s)" / "Unlimited (1-1,000,000s)"; tenant isolation High / High / Low (except single-tenant DBs); per-tenant DB cost "High; is sized for peaks" for standalone, "Low; pools used" for database-per-tenant; operational complexity of database-per-tenant "Low-Medium. Patterns address complexity at scale." (Column assignment read from the table text as extracted; verify against the page.) Same Azure SQL patterns URL.
- Azure: per-tenant schema customisation is straightforward but "The application vendor must design procedures to carefully manage schema customizations at scale." Elastic pools let databases share resources with per-database metrics; no per-database charge for pools; billed hourly for pool resources. https://learn.microsoft.com/en-us/azure/azure-sql/database/elastic-pool-overview?view=azuresql
- Azure: schema updates must be deployed across the estate and the app must know each tenant's schema version; cross-tenant reporting gets "cumbersome" (suggests a central warehouse). Storage-data page.

**Infrastructure / account / subscription per tenant (silo, "automated single-tenant deployments")**
- Azure: benefits are reduced leakage risk, no noisy neighbour, progressive rollout. Risks: "cost efficiency is low ... 100 tenants probably require 100 times that cost"; maintenance time-consuming; fleet-wide reporting. Per-tenant subscriptions avoid shared-subscription quota limits. https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/tenancy-models
- AWS: silo still uses "a shared identity, onboarding, and operational experience" (that is what separates SaaS from managed service). https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/silo-pool-and-bridge-models.html
- Azure: reasons to isolate a tenant from others: own encryption keys, individual backup/restore policies, different geographic locations (storage-data page). Azure lists Always Encrypted for tenant-supplied keys; Cosmos DB customer-managed keys at account level.

**Hybrid / bridge / cell (stamps)**
- AWS: bridge = some microservices silo, some pool; "regulatory profile ... and its noisy neighbor attributes might steer a microservice to a silo model" (Well-Architected SaaS Lens URL above).
- Azure: vertically partitioned deployments mix shared and single-tenant; risk is code must support both and you need a tenant-to-deployment map; "stamps" also work around quota limits. Tenancy-models page.
- No numeric cell-size guidance found in the pages read.

## Part 2: Agent-specific

Vendor-authored items are marked (V).

- Prompt cache isolation (V): Anthropic: "Different organizations never share caches"; on Claude API, Claude Platform on AWS and Microsoft Foundry caches are also isolated between workspaces; on Google-managed Claude and Bedrock "isolated by organization only". https://platform.claude.com/docs/en/build-with-claude/prompt-caching
- Prompt cache (V): OpenAI: "Caches are not shared across organizations and cannot be reused across regional processing boundaries"; `prompt_cache_key` separates cache reuse between groups of requests; default retention depends on Zero Data Retention (24h vs in_memory). https://developers.openai.com/api/docs/guides/prompt-caching . Implication: within one org, per-tenant isolation of cache is your job (separate workspace/project/key, or accept shared-prefix risk).
- arXiv 2502.07776, "Auditing Prompt Caching in Language Model APIs", Gu, Li, Kuditipudi, Liang, Hashimoto; submitted 11 Feb 2025, v2 13 Jul 2025 (abs page read). Abstract: detected "global cache sharing across users in seven API providers, including OpenAI", enabling timing-based inference of other users' prompts. Not vendor-authored.
- arXiv 2409.20002, "The Early Bird Catches the Leak: Unveiling Timing Side Channels in LLM Serving Systems", Song, Pang, Wang et al. (10 authors); submitted 30 Sep 2024, v5 21 Oct 2025 (abs page read). Abstract: timing side channels from shared caches and GPU memory allocation can reveal system prompts and other users' prompts. Not vendor-authored.
- Vector stores: OWASP LLM08:2025 Vector and Embedding Weaknesses: "In multi-tenant environments ... where multiple classes of users or applications share the same vector database, there's a risk of context leakage"; mitigation "permission-aware vector and embedding stores" with "strict logical and access partitioning". https://genai.owasp.org/llmrisk/llm082025-vector-and-embedding-weaknesses/ (OWASP community project, not vendor)
- Vector DB patterns (V): Qdrant: separate collection per tenant is "rarely the most efficient"; Qdrant Cloud default max 1000 collections per cluster; options are payload filter (many small tenants), user-defined shard per tenant, or tiered (promote large tenants). https://qdrant.tech/documentation/manage-data/multitenancy/ . Pinecone: one namespace per tenant; all reads/writes target one namespace; offboarding = delete namespace. https://docs.pinecone.io/guides/data/implement-multitenancy
- Shared model endpoints (V): Azure Architecture Center, Foundry Models multitenancy: compares dedicated resource per tenant (separate subscriptions: data isolation High), shared resource with dedicated project/deployment (Medium), shared resource and shared deployment (Low to medium); notes models are often stateless but Foundry Agent Service "might introduce state that you need to manage"; a dedicated subscription "alone doesn't constrain where inference processing occurs". https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/service/foundry-models
- Tool credentials (V-adjacent): MCP security best practices cover confused deputy and token passthrough. I confirmed the page lists these sections but did not read their text in full; no per-tenant credential guidance verified. https://modelcontextprotocol.io/docs/draft/tutorials/security/security_best_practices
- Memory stores / KV cache inside self-hosted inference (vLLM/SGLang prefix caching): no official guidance read. Not verified.
- NIST AI 100-2e2025 (adversarial ML taxonomy) text searched for "tenant" and "cache": 0 hits. Nothing relevant.
